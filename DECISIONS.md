# Architecture & Debugging Decisions

## 1. Root-Cause Diagnosis
What specific bottlenecks and failure modes did you observe in the original codebase under concurrent load?

- **Event-loop / CPU behavior:** `scrub_and_fingerprint()` (~40 ms of pure-Python SHA-256 looping per call on the test host) ran **synchronously inside the `async def` handler**, blocking the event loop. With 60 concurrent requests, that means ~2.4 s of serialized CPU during which nothing else, `/health` included, could run. Moving it to a thread would not fix this: each SHA-256 call hashes a 32-byte digest, and CPython only releases the GIL inside `hashlib` for inputs larger than ~2 KB, so a worker thread would still hold the GIL the event loop needs. The handler also `await`ed the downstream call (250 ms mock latency plus failures) before responding, so acknowledgment latency was tied to downstream latency.
- **Concurrency & race conditions:** There was no idempotency at all. `X-Idempotency-Key` was checked for presence and then ignored, and the `events` table had no unique constraint, so every concurrent retry produced another DB row and another downstream POST. A "check-then-insert" in app code would not fix this either, because two requests can both pass the check before either inserts. On top of that, a downstream `503` went straight through `raise_for_status()` as an unhandled exception, so the sender got a **500**. The row stayed `pending` forever, and the sender's retry created yet another duplicate.
- **Resource & connection management:** Every request opened **three new SQLite connections** (`save_event`, `mark_delivered`, plus `init_db` per process). With aiosqlite that also means a new OS thread each time. All of these competed for SQLite's single write lock in rollback-journal mode (no WAL, no `busy_timeout`), which leads to `database is locked` under burst. Every request also created a new `httpx.AsyncClient`, so there was no connection pooling or keep-alive, a TCP handshake per event, and no bounds on outbound concurrency. During the refactor I also found a subtler trap: sharing a *single* aiosqlite connection across coroutines is unsafe. Coroutine A's open `RETURNING` cursor makes coroutine B's `COMMIT` fail with `cannot commit transaction - SQL statements in progress`. I reproduced this as intermittent 500s.

## 2. Concurrency & Offloading Strategy
How did you separate CPU-bound preprocessing, HTTP acknowledgment, and downstream delivery? Why did you choose your specific concurrency primitives over alternatives?

There are three stages, connected through SQLite (the source of truth) and in-process `asyncio.Queue`s that carry only row ids as wake-ups:

1. **Acknowledgment (event loop):** validate the request, compute a cheap request hash, run one `INSERT … ON CONFLICT DO NOTHING RETURNING id`, enqueue the id, and return **202**. The event is durable before it is acknowledged. The raw content is stored temporarily in a `raw_content` column, so an acknowledged event can be recovered after a crash.
2. **Preprocessing (`ProcessPoolExecutor`):** N scrub-worker coroutines `claim` a row, run `scrub_and_fingerprint` in a process pool via `loop.run_in_executor`, then store the redacted text and fingerprint and **set `raw_content = NULL` in the same UPDATE**, so the PII never outlives preprocessing. The pool size defaults to `cpu_count - 1` so one core is left for the loop. It uses the `spawn` start method, so the pool never forks a process that already has threads, and it is warmed up during lifespan startup, before the service reports healthy. Workers run under `SCHED_IDLE` (falling back to `nice 19`), so they only use otherwise-idle CPU and the API process always wins the CPU. They also set `PR_SET_PDEATHSIG`, so a SIGKILLed parent never leaves orphaned workers behind.
3. **Delivery (asyncio + shared `httpx.AsyncClient`):** a fixed number of delivery-worker coroutines (`DELIVERY_CONCURRENCY`, default 16) bounds outbound concurrency. One pooled client is reused. 5xx, 429, timeouts and connection errors are retried with **exponential backoff and full jitter**, and the row's lease is extended before each sleep. Other 4xx responses are permanent and mark the row `failed`.

**Why these primitives:**
- **`ProcessPoolExecutor` rather than `asyncio.to_thread`:** the workload holds the GIL (see §1), so threads would still starve the loop. A process pool gives real parallelism and isolates the loop completely.
- **Not FastAPI `BackgroundTasks`:** they run in the same event loop after the response is sent, so CPU work there still blocks the loop. They are in-memory only, so a crash loses them, and they have no retry, no concurrency bound and no way to recover after a restart.
- **Own long-running worker tasks + durable table rather than fire-and-forget `create_task`:** this gives bounded concurrency, backpressure and restart recovery, a small outbox / queue pattern within the "SQLite only" constraint.
- **SQLite access:** one `sqlite3` connection owned by a dedicated single-thread executor. Each DB method runs a whole operation (statement + fetch, autocommit) as **one function on that thread**. That is one event-loop wake-up per operation instead of the 3–4 that an aiosqlite execute/fetch/close/commit sequence costs. It also makes operations atomic and serialized without asyncio locks, which fixes the shared-cursor bug from §1. `aiosqlite` is no longer needed, so I removed it from the dependencies.

## 3. Idempotency & SQLite Concurrency
How does your implementation guarantee zero duplicate processing when two identical webhook retries arrive at the exact same millisecond? What SQLite settings or constraints did you rely on?

- **The database decides, not application code.** `idempotency_key TEXT NOT NULL UNIQUE` plus
  `INSERT … ON CONFLICT(idempotency_key) DO NOTHING RETURNING id`.
  SQLite serializes writers, so of two simultaneous inserts exactly one commits and gets an id back. The other gets **zero rows** (not an exception) and returns `202 {"duplicate": true}` *without enqueueing anything*. Only the winner's row id ever reaches the pipeline. Because the constraint lives in the file, this also holds across processes. `tests/test_resilience.py::test_idempotency_across_independent_connections` fires 40 concurrent inserts of the same key through 4 independent connections and asserts that exactly one row is created.
- **Exactly one worker processes a row:** each stage takes a **lease** with a conditional `UPDATE … SET lease_until=? WHERE id=? AND status=? AND (lease_until IS NULL OR lease_until < now) RETURNING …`. Only one caller can win that UPDATE, so even if a row id is enqueued twice (by the reaper or a restart), it is processed once. Status transitions (`received → pending → delivered/failed`) are also guarded by `WHERE status = ?`.
- **Key reuse with a different body** returns **409**: a SHA-256 of the canonical body is stored next to the key (Stripe-style semantics), so a sender bug can't silently drop a different event.
- **Settings:** `journal_mode=WAL` (readers never block the writer, cheap commits), `synchronous=NORMAL` (durable against process crashes; an OS crash or power loss can lose only the last few commits), `busy_timeout=5000` (another process or reader waits instead of erroring), autocommit mode so each statement is its own short transaction, and an index on `status` for recovery scans.
- **Downstream de-duplication:** the idempotency key is also sent downstream as an `Idempotency-Key` header. Delivery is *at-least-once* by nature: if downstream commits but the response is lost, we must retry. A downstream that honors the header turns that into effectively-once.

## 4. Failure Modes & Production Trade-offs
- **What happens if the downstream service is completely unreachable for 60 seconds?**
  Ingestion is unaffected. Requests are still acknowledged in milliseconds, and `/health` stays green, because acknowledgment never touches the network. Events pile up as `pending` in SQLite. Each delivery worker retries its row with exponential backoff and full jitter (0.2 s base, 30 s cap). The retry budget is **time-based** (`DELIVERY_GIVE_UP_SECONDS`, default 15 min, with a 100-attempt safety cap). I deliberately didn't make it attempt-based: with full jitter, 8 attempts can add up to only ~13 s of waiting, which would turn a 60 s outage into failures. So a 60 s outage is always absorbed without any manual action, and because of the jitter, recovery isn't a synchronized retry stampede. Rows that exhaust the budget become `failed` with `last_error` recorded. I chose that over retrying forever so that poison events stay visible; they can be replayed by resetting the status. Throughput note: while downstream is down, the 16 delivery slots are held by sleeping retries, so new events wait in the queue (durably). `tests/test_resilience.py::test_downstream_outage_then_recovery` covers this: events arrive while downstream is down, then are all delivered exactly once after it comes up.
  *Production next steps:* a circuit breaker (pause the delivery stage instead of every row backing off independently), a scheduled `next_attempt_at` column instead of in-task sleeps, and alerting on `failed` / oldest `pending` age.
- **What happens if this service process crashes 50 ms after acknowledging a webhook?**
  Nothing is lost. The 202 is sent only after the row is committed (WAL; durable against a process crash). On restart, lifespan startup calls `recover()`, which re-enqueues every `received` or `pending` row whose lease has expired, and a periodic reaper (every 10 s) does the same for workers that got stuck. If the crash happened mid-scrub, the row is still `received` and is re-scrubbed. Scrubbing is deterministic, so there's no harm. If it happened mid-delivery, the row is still `pending` and is redelivered after the lease (30 s by default) expires. That is the one window where downstream can see the same event twice (it accepted the event but we crashed before marking it delivered), which is why the key is forwarded downstream. `tests/test_resilience.py::test_sigkill_after_ack_loses_nothing` SIGKILLs the process right after acknowledging 10 events, restarts it, and asserts all 10 reach `delivered`.
  *Trade-off:* raw PII is at rest in SQLite for the few milliseconds to seconds before scrubbing. Durability required persisting something; in production I'd encrypt that column or keep it on an encrypted volume.
- **What would break first if we deployed this container with `--workers 4` instead of 1?**
  Correctness holds: the UNIQUE constraint, the lease-based `claim`, and the status-guarded UPDATEs all live in the SQLite file, so they work across processes (tested with independent connections). What breaks first is **resources and contention**: (1) **CPU oversubscription.** Each worker creates its own process pool of `cpu_count - 1` processes, so 4 workers × (N−1) scrub processes fight over N cores. That defeats the "leave a core for the loop" design and brings back `/health` latency spikes. You'd have to set `SCRUB_WORKERS` to roughly `cpu/4`, or move preprocessing to a separate worker process. (2) **SQLite write-lock contention.** Within one process, writes are serialized by a single thread with no lock waits. Across 4 processes they contend on the file's single write lock, so commits start waiting on `busy_timeout` and tail latency goes up. (3) **Duplicated background work.** Every process runs its own recovery and reaper scans and its own 16 delivery slots, so outbound concurrency to the partner is 4× higher than intended. (4) On a shared or network filesystem, SQLite WAL locking itself becomes unreliable. The production answer is a dedicated single ingest-to-queue process plus separate worker processes, or a real queue/DB, which the constraints ruled out here.

## Verification notes
- `pytest -v -s` runs the provided burst harness plus 4 extra failure-mode tests (`tests/test_resilience.py`).
- On the original code the harness fails immediately (500s from unhandled 503s, duplicates). On this code the ingest p95 is **~55–110 ms** (target < 250 ms), there are exactly **30 rows and 30 downstream deliveries**, every row ends `delivered` with no PII, and the whole run takes about 2.5 s.
- **About the `/health < 50 ms` assertion:** I developed this in a **2-vCPU container**, where that assertion is borderline. I looked into it in detail. The harness's first probe fires at the same instant as the 60 POSTs, so it measures how long the whole burst takes to round-trip, test client included. In the same environment, the *same* probe against a FastAPI app that does no work at all measured 41–57 ms, and against a bare ASGI app that returns immediately it measured 64–115 ms. The service is at the environment's floor, and the variance comes from the client and CPU scheduling on 2 vCPUs, not from the event loop (every later probe during the run is around 10–20 ms). On a typical 4+ core machine the floor is far below 50 ms.
- **Windows is not a meaningful environment for these thresholds.** On a 4-CPU Windows 11 laptop (Python 3.14), `python diag.py` gave these numbers. The script replays the harness's burst against an empty FastAPI app and then against this service.

  | | ingest p95 | max `/health` |
  |---|---|---|
  | Empty FastAPI app (no work at all) | 449–578 ms | 415–535 ms |
  | This service | 425–513 ms | 322–425 ms |

  An app that does nothing misses both targets by the same margin, so on Windows the harness measures the OS's loopback and asyncio connection handling (no uvloop), not the service. The service adds no measurable latency on top of that floor. The thresholds are meant for the Linux container the README refers to; run `python diag.py` on any machine to see that machine's floor next to the service.
